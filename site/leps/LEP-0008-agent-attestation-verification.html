Problem statement and evidence

SPEC.md §9 "Agent attestation" (spec/01-transport.md:59-75) states the requirement in three sentences that the shipping stack does not honor:

provenance.agent.attestation is a signed token proving the agent's identity and authority. … The token is verifiable against a published key (JWKS or pinned public key). Free-text attestations are non-conformant — the token MUST be verifiable. This is a fraud-resistance requirement for high-volume agent-submitted leads. (spec/01-transport.md:61-75, condensed)

And SPEC.md §7 grades the tier on it: L3 = "full + dedup fingerprints + capability discovery + published JSON Schemas + agent binding (attestation verification)" (spec/04-errors.md:43-44).

What ships. schemas/core.json:128-137 defines the agent block as three plain strings, required-presence only (attestation is {"type": "string"}, core.json:133). The reference platform's intake (implementations/reference-platform/lcp_platform/router.py:262-298, ingest()) validates presence via _validate_envelope (router.py:1858, schema errors → "LCP validation failed"/LCP-100 at router.py:1910-1917) and never inspects the value again; the lead is persisted at router.py:359. Coverage-matrix honesty. SEC-09 is gap precisely because "a forged-token rejection test cannot exist because the behavior does not" (docs/SPEC-COVERAGE.md:187), and CNF-03's green note rests on shape checks: "attestation via L3-001" (docs/SPEC-COVERAGE.md:165). Why the envelope's own HMAC is not the answer. Transport authentication (spec/05-capabilities.md:78-109) already signs the exact request bytes (<timestamp>\n<idempotency-key>\n<raw-request-body>, HMAC-SHA256 under the per-pair secret) and LCP-012/LCP-002 already cover signature and identity failures (spec/02-envelope.md:345-348). That proves which pair secret produced this request. It cannot assert which acting principal — one publisher credential may front many agents, agents rotate, and §10's roles (spec/01-transport.md:117-122) make "agent as transporter … requires attestation ('acting for partner X')" (spec/01-transport.md:121-122) a first-class binding the transport layer structurally cannot carry. The attestation is therefore an assertion about the acting principal, signed by an authority the receiver can resolve — not a second transport MAC. This distinction drives every design decision below (asymmetric-only algorithms, aud/sender binding, and the failure-code mapping).

Adopter evidence. #192 is the interop-testing evidence required by LEP.md ("evidence from adopters or interoperability testing"): the conformance grind lane proved the gap adversarially on the reference platform. External corroboration for the demand direction: SPEC §9 itself calls attestation "fraud-resistance … for high-volume agent-submitted leads" (spec/01-transport.md:74-75) — the fraud class (forged agent provenance) is exactly what L3 exists to bind.

Proposed wire shape

1. What the attestation binds (normative framing)

The attestation asserts: principal agent_id, acting for party acting_for, at the authority iss, for the audience aud, within iat..exp — signed with an asymmetric key the receiver can resolve. It MUST NOT be used as, or replaced by, transport authentication: the envelope HMAC (§9) stays the wire authorization (§Authentication), and a receiver MUST NOT downgrade the HMAC check because an attestation verified (or vice versa). The two axes answer different questions and fail with different codes (§8 below).

A symmetric (MAC) attestation is prohibited: any receiver able to verify it can also mint it, so it carries no non-repudiable principal binding and is indistinguishable from the envelope signature the request already carries. This is why candidate trust model C (Alternatives) adds nothing.

2. Token form

Compact JWS (RFC 7519 §7.1): base64url(ASCII-header) "." base64url(ASCII-claims) "." base64url(signature), three non-empty segments, UTF-8/JSON payloads, standard base64url alphabet without padding (padded segments are decodable by parsers but MUST NOT be generated, mirroring the LEP-0002 canonical-generation discipline at spec/05-capabilities.md:111-124). Precedence is pinned: the §2 schema pattern excludes =, so a receiver rejects any padded token at the schema layer (400 LCP-100) before the verifier runs — "decodable by parsers" describes generator discipline and the base64 libraries honest producers use, not receiver leniency (revision F6b; vec: lcp-neg-attestation-padded-100).

Schema-layer tightening (lands in schemas/core.json:133, $defs/provenance → properties.agent → properties.attestation):

"attestation": {
  "type": "string",
  "pattern": "^[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+$",
  "maxLength": 8192
}

The pattern is shape validation only (three non-empty base64url segments); everything above shape is verification (§5), which the schema cannot express. Free-text values therefore fail early with the present class of error (LCP-100, field: "provenance.agent.attestation"), while JWT-shaped junk fails verification (LCP-002) — see §8.

Header requirements: alg MUST be present and in the allowlist (§3); kid MUST be present (key selection, §4); typ SHOULD be JWT. A b64 header or detached signature (alg:none, empty signature segment) is non-conformant (and the empty third segment already violates the §2 pattern).

Receiver-side header policy (re-dossier R4; decided at §5 step 2, the shape step — generation-side typ stays a SHOULD, unchanged): typ is OPTIONAL on receipt and MUST NOT decide a verification outcome — its value never admits a token, and a non-JWT value (at+jwt, RFC 8725-style) MUST NOT reject one (JWT and at+jwt variants of identical claims verify identically). §6's claims analogue ("others … Ignored") is hereby mirrored to headers: receivers MUST ignore header members outside alg/kid/typ, and MUST NOT dereference URL-bearing members (x5u, x5c, jku) — §5 step 7's iss → JWK[kid] resolution (or a configured pin) is the only key-resolution path. crit is the one member that MUST NOT be ignored: this profile defines no extensions, so any crit header names an extension the receiver cannot understand — unknown crit-adjacent members are a format failure at step 2, not silence.

3. Algorithm allowlist (closed)

alg Key type Status
EdDSA OKP/Ed25519 MUST be supported; RECOMMENDED default
ES256 P-256 EC MUST be supported
HS256/HS384/HS512 (any MAC) — MUST be rejected — reason algorithm
none, or anything outside the table — MUST be rejected — reason algorithm

Rationale in §1; the MAC-rejection rule also closes the classic algorithm-confusion attack surface (an attacker re-signing with the public key as a symmetric secret). Receivers MUST read alg from the header only to select a verifier from this allowlist, and MUST derive the expected algorithm from the resolved JWK's alg when present (mismatch → algorithm). The allowlist test is an exact, case-sensitive string match performed at §5 step 3, before any key lookup: no trimming, case-folding, aliasing, or post-lookup relaxation — "edDSA", "EdDSA ", or "ES256"-shaped-with- whitespace are algorithm failures, and a token that fails step 3 MUST NOT cause issuer resolution (§4) to run.

Signature encoding (normative; revision F3). An EC signature is the IEEE P1363 fixed-width r ‖ s concatenation per RFC 7518 §3.4: for ES256 each of r and s is the field-element magnitude left-padded with zeros to 32 octets, big-endian — the signature is exactly 64 bytes. DER (ECDSA-Sig-Value SEQUENCE) and any other variable-width encoding MUST NOT be accepted: a receiver that accepts DER and one that accepts only JWS canonical bytes reject each other's valid tokens (70–72-octet DER — length depends on the top bits of r/s — vs a fixed 64-octet r ‖ s for the same signature; both observed, see Revision battery), which breaks the determinism this record sells. Width is checked before the cryptographic verify (step 8 precheck → format); a correct-width buffer that fails the math fails signature. EdDSA signatures are likewise fixed-width (64 bytes, crypto_sign output; no alternative encoding exists). Implementation-phase gates: plat: test_attestation_es256_der_rejected (V17) and an ES256 positive vector in the V8 family (V8 amended below); fixture note: the vector lane ships an ES256 fixture keypair derived deterministically from a published seed — private scalar d = int.from_bytes(SHA-256("lep-0008-fixture-p256-seed"), "big") on P-256 (valid scalar; pinned kid attest-es256-1) — mirroring the reproducible- from-seed property of the Ed25519 fixture above; the implementation PR publishes the resulting public JWK, and reviewers re-derive every ES256 vector byte-for-byte as they do the Ed25519 ones (executed in the Revision battery).

4. Key distribution — RECOMMENDED trust model (settles #192's open item)

spec/01-transport.md:72-73 names "JWKS or pinned public key" but defines no surface. The record settles on:

Canonical: issuer-published JWKS over HTTPS. iss is an HTTPS issuer URL under the publisher's or agent-authority's control; the verification document is resolved deterministically as jwks_url = iss + "/.well-known/jwks.json" (RFC 8615 path, per-issuer). Rules the implementation MUST honor:

Resolution Fetch over TLS 1.3 (§9 Transport, spec/05-capabilities.md:74-76); MUST NOT fetch before the request is transport-authenticated (unauthenticated callers get LCP-012/LCP-002 first — no fetch amplification). Egress is guarded by the paired controls exactly as shipped on the delivery path (router.py:1019-1028) — the pre-resolution string check alone is NOT the guard: every JWKS fetch MUST (a) pass validate_webhook_url (security.py:16) tightened to HTTPS-only (the shipped class permits http under allow_insecure_webhooks; attestation resolution MUST NOT, in any mode) with no user-info in the URL (already enforced: "must not contain embedded credentials", security.py:20-21); (b) pass validate_egress_host (security.py:33) — the resolve-aware leg, in every deployment mode: the attestation fetch MUST NOT inherit the shipped class's allow_insecure_webhooks skip (security.py:42-43 returns before getaddrinfo; security.py:66-67 short-circuits the predicate block), so no insecure-webhook escape hatch applies to a JWKS fetch, test_mode sandbox deployments included (config.py:86 — the flag is reachable only there; re-dossier R1): getaddrinfo the hostname and reject is_private/is_loopback/is_link_local/is_multicast/is_reserved/is_unspecified post-resolution (security.py:44-54, 66-74), which is what kills the obfuscated-literal class the string check waves through (https://2130706433, https://0x7f000001, https://127.1, https://localhost all map to 127.0.0.1 at getaddrinfo and pass validate_webhook_url — executed, Revision battery); (c) follow_redirects=False — a 3xx from a policy-valid issuer is NOT followed (revalidation of a final URL is NOT an acceptable alternative at v1; the shipped delivery client is the precedent); and (d) trust_env=False — no HTTP(S)_PROXY/env interception of the fetch. These four are MUSTs on every outbound fetch attempted on the verification path — the JWKS dereference by verifiers included, not just "the JWKS fetch" as a service routine — including negative-cache retries (re-dossier R4: header bytes are attacker-chosen, so any egress an implementation might otherwise trigger from them, e.g. a library-side x5u dereference, inherits this guard; the §2 header-member rule forbids that dereference outright, so the paired controls guard the one path that legitimately exists). Residual DNS-rebinding TOCTOU (resolve at check ≠ resolve at connect) is named, not claimed closed: connection-pool reuse and re-resolve hardening are implementation-PR concerns; the no-redirect/no-proxy legs remove the two same-process escalation paths. Policy-invalid iss → rejection reason issuer_policy (a sender-fixable identity failure, §8).
Selection kid (required, §2) selects the JWK; kty/crv/alg of the selected JWK MUST be consistent with the header alg (§3 allowlist). No key found for kid in a successfully fetched valid document → key_unknown. Duplicate kid entries. The keys array MAY be malformed — two JWKs carrying the same kid give first-wins and last-wins implementations opposite answers for the same token (determinism broken across conformant receivers; dossier F5). A norm is required; two conformant resolutions exist and this record refuses to silently pick: (A) a document containing two JWKs with the same kid is an invalid document → routed with the Bounds row: fetched-but-invalid → LCP-002/401 key_unknown — this also covers the use/key_ops confusion class (a use:"enc" key selected for verification is likewise an invalid-document case); (B) selection is pinned to first-match in document order and the receiver MUST log a duplicate_kid warning — deterministic, more forgiving of honest issuer mistakes, but keeps serving tokens under a document the issuer shipped broken. Both options carry the same named-shape gate (plat: test_attestation_jwks_duplicate_kid_rejected asserts A; under B it becomes …_first_match_pinned). Marked for the maintainer at Accept (design decision, not a text fix); the reference implementation and Revision battery validate A (the stricter, closed-vocabulary-consistent option).
Bounds JWKS document ≤ 16 KiB, ≤ 32 keys (format sanity, mirroring the LEP-0003 32-entry report bound); token ≤ 8192 bytes (§2 maxLength). Outcome attribution (revision F4, §8 blame rule): the bounds above are format sanity, not availability — a successfully fetched document that is oversized, key-count-exceeding, non-JSON, or otherwise invalid is a sender/issuer-fixable state and MUST fail the token: LCP-002/401 key_unknown (closed vocabulary preserved; a dedicated jwks_oversize-style reason was considered and rejected as vocabulary bloat for a state already named). LCP-500/500 key_unavailable is reserved for availability failure only: DNS/connect error, timeout, or a 5xx response from the issuer (the server itself failed). A 4xx (e.g. 404 on the /.well-known/jwks.json path) is the issuer's configuration — routed as fetched-but-invalid: key_unknown/401. An issuer serving garbage or pointing at a missing path must not convert its own fixable state into receiver-class 500s on every verified sender's request.
Cache Cache per (iss, kid); respect HTTP cache-control/max-age, hard cap 24 h; negative cache for fetch failures ≤ 30 s. Fetch timeout ≤ 2 s, and MUST NOT block the intake worker beyond it (bounded worker, else key_unavailable).
Rotation Routine rotation = new kid alongside the old in the same JWKS; deployments MAY keep the previous key for a bounded window (mirrors §9's "During key rotation, a receiver MAY accept a previously active secret", spec/05-capabilities.md:108-109). No protocol change needed.
Compromise Issuer removes the kid; propagation = cache TTL. Blast radius is per-issuer (each issuer publishes its own keys) — never global.

Fallback: pinned public key (deployment configuration). A closed publisher↔buyer pair MAY configure iss → pinned JWK locally (the §9 "pinned public key" leg). The pin replaces resolution for that issuer and is otherwise identical. Pins live in receiver deployment config — not a new protocol/registry surface; registering sender-scoped keys as a canonical protocol surface is Alternatives B (rejected as the primary, with reasons).

Why issuer-anchored, decided against the candidates (full trade-off table in Alternatives considered): §9's issuer claim ("Authority that issued the token") only means something if the receiver can resolve it; agent-as-consumer/agent-as-source topologies (§10, spec/01-transport.md:117-125) put a single agent authority across many publishers, which per-pair registration cannot model without inventing a registry; and the reference platform ships zero discovery surface today, so both models pay bootstrap cost — issuer JWKS pays it once per issuer and gets revocation via rotation for free.

5. Verification procedure (reference algorithm — executed in the battery)

Runs once per newly accepted lead, at a pinned intake slot: after auth.authenticate and the per-sender rate limit (router.py:279-295, LCP-011 at router.py:295) and after the idempotency dedup lookup (router.py:297), but before insert_lead (router.py:359) — the same ordering principle as §9's "Receivers MUST reject requests outside the acceptable timestamp window before processing PII" (spec/05-capabilities.md:105-106): a failed verification MUST NOT persist PII. Placement relative to the two early-return paths in the dedup block is normative: the LCP-005 mismatch 409 (router.py:304-308) and the DUPLICATE ack (router.py:318) both short-circuit before this procedure runs, so a DUPLICATE ack never re-verifies and never fetches keys (the bytes were verified at the original accept, whose verification gated the row that now produces the ack); an idempotency-key collision likewise fails on the idempotency axis without touching the issuer. Verification happens exactly once per lead, at its first acceptance attempt. source_type != "agent" or an absent provenance.agent block → the procedure does not run (presence semantics unchanged, core.json:135).

Steps 2–5 are decode-time steps: they run on parsed structure and MUST complete before any key lookup, network fetch, or cryptographic evaluation — no implementation may let a signature-verified token smuggle a malformed claim set into the signature-time evaluation of steps 9–12, and no implementation may do cryptographic work for a token that will fail on shape alone.

Parser rule (duplicate claim names, normative). Header and claims MUST be parsed with RFC 8259 §5 duplicate-name rejection (e.g. Python json.loads(..., object_pairs_hook=…) that refuses a repeated key; equivalently any strict parser configured to reject, not last-wins). A token whose claims object carries "aud" twice with different values is a format failure at step 2 for every conformant receiver — an implementation that last-wins would accept the token at one receiver's aud and reject at another's (the divergence the dossier executed). Step 4 must therefore never see a duplicate, and no claim evaluation may define winner selection among duplicates.

Depth (re-dossier R2). The refusal applies to every JSON object in the header or claims serialization, at any nesting depth — the object_pairs_hook example fires per object, innermost first, so a repeated member inside a nested claim value ({"meta":{"tier":"gold","tier":"platinum"}}, validly signed) is the same format failure at step 2. This is the stricter of the two readings the re-dossier executed (the whole-document scan of the two top-level objects accepts it); both are deterministic, so the record chooses and states the rule rather than leaving the depth to library defaults.

Reason vocabulary (normative, closed): format, algorithm, issuer_policy, key_unknown, key_unavailable, signature, expired, audience, claims_mismatch. Evaluation stops at the first failing step — the order is deterministic so the same forged input always yields the same reason (re-executed post-revision against the 13-step procedure: an expired and claims-contradicting token still reports expired, Revision battery).

Step 12 reuses the shipped scope machinery (auth.py:187-189 has_scope, scope strings per sender, storage.py:502): act_for:<party> is a scope string in the existing credential registry, not a wire field — an agent submitting with its own sender credential (agent_pub_001 on behalf of pub_123, the L3-001 topology) verifies iff the delegation was registered. 7. Replay, clock, and window rules (units-precise)

Units (normative).

Quantity Unit Definition
one attestation one signed assertion exactly one (agent_id, acting_for, iss, aud) tuple per token; a token asserting two principals is not expressible (single claim set).
one verification per lead acceptance exactly once per lead, at the first acceptance attempt, at the pinned §5 slot; a retry of an already-accepted envelope returns the DUPLICATE ack without re-verification (the original accept verified the bytes that minted the row — §5 placement; plat: test_attestation_duplicate_ack_never_refetches); a retry that did not previously reach acceptance verifies normally (deterministic result, cached keys).
one failure exactly one reason first-failing step of §5 wins; no multi-reason payloads.
token validity seconds exp − iat, issuer-chosen; the protocol bounds only the acceptance window (§5 step 9's skew ≤ 30 s). The RECOMMENDED maximum lifetime is 900 s (advisory; normativizing it is Deferred with data).
replay window (transport) 300 s default unchanged §9 HMAC window (spec/05-capabilities.md:107, config.py:33); the attestation rules are independent of it.
agent-evaluation window 30 s default §9 agent-as-consumer (spec/01-transport.md:104-111), pinned "exactly 30" by the #195 lane (implementations/reference-platform/tests/test_gap_security.py:491-517; default ping_timeout_seconds 30, messages.py:140). Chosen as the ceiling for clock-skew allowance so no token accepted at intake can have been expired longer than one transaction window.

Clock rule. exp is compared against the receiver's wall clock in NumericDate seconds. Expiry boundary (revision F7): the check fails expired when now ≥ exp + skew — rejected at equality; this is a deliberate asymmetry with the shipped transport window, which accepts at equality (abs(Δ) ≤ max_skew_seconds, auth.py:70-71 — that boundary is unassigned pending #143 per docs/err-auth-triage.md §2, and this record does not silently harmonize it). An expired token carries no authority even for one second, while a transport timestamp within the window is still replay-protected by the idempotency machinery — so strictness on the authority axis and laxity on the freshness axis are consistent, but the conventions differ and both are now named. Skew allowance: deployments MAY configure skew ≤ 30 s (default 0) and MUST NOT configure more — the cap is a MUST enforced at configuration time, not advisory (plat: test_attestation_skew_config_capped_at_30); its ceiling is the agent-evaluation window row above, and the reason the allowance exists at all is NumericDate whole-second truncation: a token minted anywhere inside a second and verified anywhere in a later clock tick of the receiver can legitimately appear up to one second early (plus honest clock drift); the ≤ 30 s bound keeps the total slack under one transaction window so no token accepted at intake can have been expired longer than the platform will wait on an agent anyway. No iat freshness requirement at intake — a 5-minute-old valid token is expected behavior (agents batch many submissions), which is why per-token single-use caching (jti replay cache) is deliberately absent: the transport replay defenses (envelope HMAC over exact bytes + idempotency-key equality + replay window — all shipped and pinned by the #195 lane's SEC-06 tests) already stop request replay; a reused token inside its exp on new envelopes is the intended use, and cross-receiver reuse is killed by aud (step 10). A jti cache would add unbounded state to defend a non-threat; the Deferred trigger covers the case where forwarding or exfiltration evidence changes that calculus.

Cross-pair/cross-receiver replay (the binding #192 asked to settle). (aud, iss→kid, acting_for==sender|scope) together mean: a token minted for platform_001 fails at platform_002 (audience); a token minted by publisher A's authority fails at publisher B's submissions (claims_mismatch/ key_unknown — B cannot even produce issuer A's signatures because the algorithms are asymmetric). No new state required.

Privacy, security, and universal-core audit

PII boundary. provenance.agent.* sits in the provenance object that §3 defines as non-PII (spec/03-payloads.md:105). The proposal adds no PII and adds two MUST-NOTs: the claims set MUST NOT embed consumer identifiers or contact data (anything verifiable cross-pair via aud/iss is a correlation vector), and logs/telemetry MUST NOT retain full attestation values (a token is replayable bearer-grade material until exp — never the signature bytes). What audit and telemetry rows DO store is now a frozen schema (revision F8, interlock with LEP-0005, which makes audit_events interop-readable for the first time — unspecified metadata would become public surface): {outcome, reason, iss_host, kid, tok_sha256_16} — outcome ∈ accept/reject/observe, reason from the closed §5 vocabulary, iss_host the issuer URL's host component only, kid the header claim, and tok_sha256_16 the first 16 hex characters of SHA-256 over the full compact token bytes (input definition normative, so two deployments can correlate incidents). No other attestation-derived field is admissible, and the token (or any segment of it) MUST NOT appear in audit metadata, metrics labels, or logs. Because aud/iss are per-deployment identifiers and tok_sha256_16 is truncated one-way, the schema is not a correlation vector across receivers. LEP-0005's history projection keeps the same rule from the read side ("never return raw envelope bodies"), and the joint obligation is asserted in one place: plat: test_history_projection_never_emits_attestation_bytes (V23). The lead store already persists the block under §3's storage rules, spec/01-transport.md:82-89 PII posture applies unchanged since the field is not PII.

Abuse cases engaged:

  • Forged agent provenance (the #192 class): closed by verification + algorithm allowlist + asymmetric-only keys.
  • Cross-pair token transplant: closed by aud + issuer-key binding (§7) — a token cannot be shown to a receiver it was not minted for, and other senders cannot mint issuer A's tokens.
  • Algorithm confusion: closed by the allowlist derived from the resolved JWK (§3), not from attacker-chosen alg alone.
  • SSRF / fetch amplification via iss: closed by auth-before-fetch, the paired egress controls (§4 Resolution: validate_webhook_url HTTPS-tightened + resolve-aware validate_egress_host post-resolution rejection, follow_redirects=False, trust_env=False — the shipped delivery-path pattern, router.py:1019-1028), size/count/TTL bounds, and a 2-second bounded fetch. The pre-revision text named only validate_webhook_url and over-claimed: the string check accepts https://2130706433 / https://0x7f000001 / https://127.1 / https://localhost, all of which resolve to 127.0.0.1 (executed, Revision battery); the egress leg is what rejects them. DNS-rebinding TOCTOU between policy check and connect remains a named residual (§4), with the redirect/proxy legs removing the in-process escalation paths (revision F1).
  • Fail-open temptation: prohibited — enforce mode MUST NOT substitute an accept when key resolution fails; the sanctioned soft path is the explicit observe phase, which logs but does not record a conformance claim.
  • Log-replay of captured tokens: mitigated by the log-hygiene MUST-NOT; residual risk (store contents = replayable until exp) is bounded by short recommended lifetimes and aud binding, with jti single-use Deferred (its trigger names the day tokens get forwarded).

Universal-core audit (§12, spec/01-transport.md:165-191). No new core field — tightening the form of a shipped required string is a validation change, not a namespace addition; tools/check_reserved_fields.py and tools/check_universal_core.py gates listed under Verification runs pass unchanged on this record (docs-only). The verification machinery lives at platform/deployment level; agents stay out of core (§10 "never coupled into the core", spec/01-transport.md:112-115). Nothing executable crosses the wire (no matching rules — decision rule honored); act_for: is a scope string in the existing credential registry, not an expression.

Trust-model security statement. Verification moves the fraud-resistance anchor from "the pair secret can sign anything" (envelope HMAC — true today; a compromised pair secret produces perfectly-looking traffic) to "an issuer-controlled key asserts the principal" — strictly better for agent fraud, and explicitly not a repudiation guarantee against the publisher itself (the publisher controls its issuer keys and could mint any claim; the binding is per-issuer). The record refuses to overclaim this in §9 text; stronger non-repudiation requires the deferred third-party trust models.

Rollout, migration, observability, and rollback

Staged; each phase is independently shippable and observable. The phases are the answer to #192's warning that "rejection changes published behavior" — they sequence who is inconsistent when.

Phase 0 — advertisement honesty (bug-class PR, lands BEFORE this MINOR; the one decision in this record adjacent to wire-visible output that the maintainer must ratify early). One-line reference-implementation change: conformance_level: "L3" → "L2" at router.py:1769, plus V12's pin test and a CNF-03/SEC-09 note update. It restores published behavior (§7 already excludes non-verifying endpoints from L3; spec/04-errors.md:43-44) — the LEP.md rule that bug PRs may bypass the LEP path applies to this step alone, and the record flags it explicitly because the maintainer, not this lane, makes that boundary call. No adopter can be harmed by a more honest capability string under §8's parsed-semver comparison (nothing in the spec keys behavior off L3). MCP/SDK test fixtures pinning the literal (the stub dict at test_gap_mcp_surface.py:128) are test-double data and stay green (verified in the battery run of the tree as-is; the adapter passes through whatever the platform returns).

Phase 1 — wire (this record, post-Acceptance): SPEC §5/§7/§8/§9 text; core.json form tightening; vectors + fixture JWKS; SDK helpers; implementation PRs link this LEP + registry row per the traceability gate; the tightening's CI-visible effect is confined to non-conformant fixtures (L3-001 re-issued).

Phase 2 — observe mode (deployable before flipping enforcement): verification runs everywhere in enforce-capable deployments with mode=observe: every §5 procedure outcome is recorded ({outcome, reason, iss_host, kid, tok_sha256_16} — frozen §Privacy schema, never the token), leads still accept, zero new rejections on the wire. This phase answers the question this Draft cannot: how much accepted traffic actually carries verifiable tokens today? Field counts on observe mode (and adopter reports solicited on #205) are the evidence; the unit is the ingest attempt, and the exit criterion is the reason-mix being dominated by format/algorithm (i.e. junk, not honest senders mid-migration) with the expired/signature classes at noise levels for an agreed interval (deployments set; suggested review point: 2 weeks).

Phase 3 — enforce: mode=enforce becomes the conformance-relevant default (spec-level: verification is mandatory at §9's MUST; a deployment running observe mode is not L3-honest and must not advertise L3 — same rule as Phase 0). Per-sender grandfather windows are deliberately not proposed: §9 already said free text is non-conformant since v1.0, and soft-per-sender exceptions are exactly the "vendor-specific defaults" LEP.md exists to prevent. A deployment that needs migration grace stays in Phase 2.

Observability (all phases): counters per §5-reason; issuer-fetch latency/error gauges; LCP-500 rate alert (issuer outage), audit rows on verification failure with reason; no token bodies in any of the above (privacy audit).

Rollback: Phase 3→2 (mode flag) is the primary lever — accept behavior returns byte-identical to today's wire while verification continues to record. Phase 2→1: verification disabled entirely (flag), schemas keep the pattern (free-text senders still break at the schema line — the tightening and the verifier are separable but the pattern was already implied by §9; a full schema rollback is redeploying the prior bundle, no data migration exists). Phase 0 is never rolled back (an honest advertisement is not a regression). The reference lcp_versions advertisement is unaffected by rollback direction — nothing gates v1.1 fields on this feature, so no negotiation trap opens mid-rollout (unlike the LEP-0003 slot fields).

Migration (senders): conformant senders do nothing (they already mint verifiable tokens); non-conformant senders adopt an issuer key + mint per §2/§6 — the SDK helper is the on-ramp; observe-mode counters tell each publisher exactly which of their agent stacks fail which axis, before a single request starts rejecting.

Deferred questions

Each with its revisit trigger — none blocks this proposal:

  1. Buyer-side (agent-as-consumer) attestation. Today verification binds the submission direction only; a buyer's agent accepting a delivered post acts under the buyer's receiver-side credentials, and the submission attestation MUST NOT be treated as buyer-side authority (direction rule, §7). Trigger: any platform ships agent-consumer acceptance with delegation needs (marketplace lane, LEP-0006 surfaces) or a dispute turns on "which buyer agent accepted".
  2. jti single-use replay cache. Refused at v1 as unbounded state defending a threat already closed by aud + envelope HMAC + idempotency (§7). Trigger: evidence of captured-token replay within exp, or the attestation ever being forwarded beyond the receiver (then reuse becomes the security boundary).
  3. Forwarding attestations downstream (platform → buyer posts with the agent provenance block): currently out of scope (provenance rides the lead where a deployment chooses); forwarding changes the replay calculus (item 2) and the log-hygiene surface. Trigger: a buyer requests verifiable provenance without contacting the platform.
  4. DID / cross-platform trust lists / third-party issuer registries (Alternatives D): Trigger: agent identity portability across platforms becomes an adopter ask, or issuer-key compromise blast radius proves insufficiently local.
  5. act_for: delegation as a registered interface (discovery, multi-tenant scope hygiene, delegation chains): today an out-of-band registry string. Trigger: second adopter builds agent-scoped senders (evidence solicited on #205) or chains-of-agents appear.
  6. RSA (RS256) expansion (§3 allowlist): Trigger: a production issuer demonstrably without Ed25519/P-256 keys.
  7. Normativizing a maximum token lifetime (recommendation 900 s today): Trigger: Phase 2 field data on real lifetimes.
  8. A §8 capability flag for enforcement mode (observe vs enforce): refused at Draft because senders gating on it would normalize soft mode; Trigger: interop evidence that mode-gating saves a migration — at which point the L3 advertisement rule (§9) needs re-review too.
  9. iat/nbf freshness enforcement (short-validity pressure on honest-but-lazy issuers): Trigger: Phase 2 data showing long-lived tokens dominating real traffic.
