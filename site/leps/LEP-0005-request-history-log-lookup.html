Problem statement and evidence

Trigger (verbatim, roadmap Phase 6). "platform operators and publishers need to inspect past ping and post requests (for debugging, dispute resolution, or compliance audits) without paging through raw database dumps." The reference pattern the roadmap cites is a commercial US home-services network's paginated GET log endpoint "filtering ping requests by ID, response status, caller phone, response phone, and time range, with pagination metadata in response headers," and the design constraint LCP adopted: "expose a filtered, paginated read surface (REST and MCP) over it. Never return raw envelope bodies or PII in the log surface — return metadata (status, token, timestamps, sender, need/vertical, price) and redact or hash contact fields. Additive; no core change."

Internal evidence — the data already exists; the surface does not. "Exists" means stored: the row universe is exactly the backing tables named in the projection mapping below, and response artifacts that are constructed but never persisted (acks, messages.py:65) mint no rows and are cut from v1. With that scoping, the reference platform already records, in first-class tables, everything the roadmap names as metadata:

  • leads (storage.py:512) — message_id, sender_id, receiver_id, message_type, status, vertical, test, created_at/updated_at;
  • pings (storage.py:623) — per-buyer ping records with status (OPEN/EXPIRED/WON/SUPPRESSED, e.g. storage.py:2102, storage.py:2146, storage.py:2173) and expires_at;
  • bids (storage.py:635) — decision (accept/reject/pass, schemas/bid.json), bid_price_cents, currency, received_at;
  • deliveries (storage.py:650) — outbound post/event delivery state (PENDING/RETRY/DELIVERED/FAILED, REDACTED after erasure per storage.py:2726-2732) with attempts and last_error;
  • match_decisions (storage.py:614) — explainable routing decisions per (lead, offer) with reasons (already surfaced per-lead by lead_status, router.py:1660);
  • dead_letter_jobs (storage.py:718) — exhausted jobs with recovery state, listable today only through the operator CLI (admin.py:38-41 → list_dead_letters, storage.py:1778-1803, ordered created_at, job_id);
  • audit_events (storage.py:732) — actor/action/resource records written by insert_audit (storage.py:1048) with the correlating X-LCP-Request-Id folded into metadata_json (storage.py:1060-1062); a reader exists internally (list_audit_events, storage.py:1085) but is keyed only by (resource_type, resource_id) and is exposed on no interop surface.

Today's only protocol-level read surfaces are GET /v1/lcp/leads/{lead_id} (role-filtered detail view, service.py:167-172, router.py:1646-1728), GET /v1/lcp/offers (+/quota), GET /v1/lcp/capabilities, GET /v1/lcp/schemas/{name}, GET /v1/lcp/attachments/{id}, /metrics (platform:admin-gated, service.py:147-149), and the health endpoints (service.py:137-174). Enumerating them: there is no way to ask "what happened around lead X / between time A and B / for phone hash H" without raw database access or shell access to admin.py. lead_status answers "this one lead, now"; the dead-letter CLI answers "this queue, all of it". Neither answers a dispute ("this consumer called on Tuesday; what did each party see and when?") that starts from anything other than a known lead_id.

External evidence — honest scope of the claim. The comparison network runs this mechanism in production today (roadmap Phase 6 header, 2026-08-18): a single-buyer ping/post network whose log lookup exists precisely because dispute resolution across two organizations — "the network says the ping went out, the publisher says it never came back" — cannot ride one party's private SQL. That is one external production datapoint plus the roadmap trigger wording. No independent LCP adopter has yet recorded evidence on this surface, and this Draft is explicitly soliciting it on #187 before Review closes. Contrast with LEP-0003: there the interop necessity (slot dedup) rode a shipped core block (exclusivity); here the necessity argument is operational. Note also the decision-rule scope precisely: the two-adopter/interoperability-necessity bar in governance/LEP.md gates a new universal message type. This proposal adds zero message types, zero envelope fields, and zero vertical changes — it is a REST/MCP read surface over existing stored state. What makes it LEP material instead is the other list in LEP.md: it touches a PII boundary (exposing contact-derived data as hashes), an authentication rule (new scope), and a retention interplay (§9 erasure). Those boundaries are why "just ops tooling" cannot be waved through as a normal PR (see Alternatives).

Scope

  • Reference implementation + transport binding: a new read-only endpoint GET /v1/lcp/history/requests on the reference platform's dispatch table, an MCP tool get_request_history on the existing thin adapter, and the OpenAPI path describing both. Row content is metadata already stored (status, ids, timestamps, sender/receiver, vertical, price) plus one contact-derived value under a strict per-pair rule; never raw envelope bodies.
  • New read scope: history:read, enforced through the existing _authenticate_read gate (service.py:174-181, auth.py:181-185) plus row-level scoping (who may see which rows — the scope matrix below), mirroring the existing precedent that lead:read alone is not enough (authorize_lead_read, router.py:1646-1658, filters by counterparty). Honest delta the post-dossier revision records: the shipped authorizer binds the counterparty, never the tenant — the row-level tenant equality in the matrix is a new obligation of this surface, not inherited behavior (see "Tenant binding at query time", #202 F2).
  • SPEC text (implementation-phase, gated on acceptance): one paragraph in §9 (PII subsection, spec/01-transport.md:82-89) norming the history read surface's contact-hash rule, and a history entry in the §8 capability shape (spec/04-errors.md:46) so callers can discover the surface.
  • Schemas: a new response-shape schema (schemas/history-request-row.json, drafted below) — not a message payload schema; the eight schemas/*.json envelope files are untouched.
  • Conformance/vectors: platform behavior tests named below; a row-shape vector family; MCP parity.
  • Not in scope: any change to message envelopes, the closed message type enum, vertical schemas, the delivery/routing pipelines, replay or re-drive operations (dead-letter quarantine/replay stay CLI-only at storage.py:1804-1816), bulk export or archival download (Deferred questions), publisher-side visibility into other parties' ping/bid rows (Deferred questions), and any write surface (this endpoint mutates nothing, including audit_events aside from logging the query itself).

Rows carry no consumer, location, attributes, or envelope members — the roadmap's "never return raw envelope bodies or PII" is the schema's additionalProperties: false, not a scrub pass. Post-dossier, the claim is scoped to exactly what additionalProperties buys: it closes members, not text inside allowed strings. lead_id is publisher-supplied free text whose shipped constraint is literally {"type": "string"} (schemas/lead.json:16-18, §4 lead), and erase_lead retains it (storage.py:2800-2805), so a contact planted inside an identifier can survive both the envelope validator and an erasure. The honest property of the closed shape is therefore "no contact fields"; contact-shaped text is blocked by the identifier pins of rule 6 below, a bounded heuristic rather than a structural impossibility — the residual risk is named there, not waved away.

What "redact or hash" means, precisely

The roadmap constraint says "redact or hash contact fields". The two are different privacy guarantees and this record picks one per field instead of leaving the choice to implementers:

  1. caller_phone_hash is a hash with the pair secret, not a redaction. Exactly the §9 phone_hash model (spec/05-capabilities.md:134-140; spec/01-transport.md:7-13) that LEP-0003 §3 extended to contact hashes (spec/01-transport.md:15-45): caller_phone_hash = HMAC-SHA256(pair_secret, verbatim wire consumer.phone) — the platform-side instance already shipped as pair_phone_hash (messages.py:48-62), keyed per pair so the same phone yields a different digest per credential and an intercepted digest is non-reversible without that pair's secret. Computed at read time from plaintext the platform still holds, never stored in history rows — the re-key-from-held-plaintext-only rule of LEP-0003 §3 / the shipped contacted-digest re-key path (router.py:718-747) is the precedent. The read-time rule is what makes erasure correct by construction (see Retention below).
  2. Absent where no pair secret exists. A caller credential with no bilateral HMAC secret (e.g. API-key-only, hmac_secret NULL, storage.py:504) cannot receive a keyed hash for anyone's phone — the field is omitted from every row for that caller, not zeroed and not plaintext.
  3. Absent where no plaintext remains. Erased/redacted leads carry no computable hash (storage.py:2688-2742 redacts envelopes; the preimage is gone) — rows persist for auditability of the erasure itself (storage.py:2690-2693, lead.erased audit event at storage.py:2778-2787) but every contact-derived field is absent.
  4. Everything else is redaction-by-omission. No email, name, address, or postal-derived field appears on a row in any form; a keyed email filter parameter stays deferred behind the §9 email gate (Deferred questions).
  5. Never unsalted digests — same MUST as LEP-0003 (roadmap: "Adopt the mechanism, not the hash"; §14 blocker B3 lineage). SHA-1-shaped values in parameters or rows are conformance failures (invalid C below).
  6. Identifier text is pinned at the projection, not trusted at the source (post-dossier rule, #202 F1). lead_id is publisher-supplied and protocol-legal whatever the publisher mints — the shipped lead schema constrains it exactly as {"type": "string"} (schemas/lead.json:16-18) — and erase_lead's redaction whitelist retains it (storage.py:2800-2805). The ARB lane executed the consequence: a lead whose lead_id is "+15559876543-jane.q.public@example.com" passes the shipped SchemaValidator, ingests, erases, and its history row still carries the phone and address verbatim (dossier attempt 7 / invalid F below). The row schema therefore refuses, at emission and at query time, any lead_id that matches §3's contact shapes — (i) a run of 10–15 digits starting the value or not preceded by a letter/digit/hyphen (the national-number form of the E.164 pattern pinned at schemas/core.json:17 and the shape of a phone pasted into an id), (ii) a value consisting only of digits and phone punctuation (^[0-9 .()+-]{10,}$ — a formatted phone), or (iii) an email address (the consumer.email form, schemas/core.json:16) — and bounds every free-text identifier field (status, sender_id, receiver_id, vertical: anchored charset + maxLength 64), so no unbounded or contact-shaped string reaches a counterparty. The run-detection is deliberately narrower than "any digit soup ≥10 chars": hyphen- or letter-delimited digit segments (uuid-tail ids, lead_20261103-0001 date-sequence ids) PASS — the revision battery showed a wider run regex misfires on them, and silently omitting the join key from 0.4% of legitimate uuid-shaped ids is a worse audit failure than the residual it accepts. Legacy nonconforming ids — decision: omit, do not coerce. For a stored row whose lead_id fails the pin, history emission MUST omit the lead_id member (same absent-never-blank discipline as rule 2); the row itself survives with request_id as its handle. Coercion is rejected on evidence, not taste: (i) truncation or casefolding invents a collision namespace — two consumers' distinct ids can fold to one pinned value, fabricating a false join on a dispute-resolution surface, which is strictly worse than an absent field; (ii) a hashed substitute would be a new disclosure oracle requiring its own per-pair keying argument (the LEP-0003 analysis) this LEP does not open; (iii) no caller loses recourse — the publisher that minted the id still holds it via its own ingest ack and lead_status, and the stored envelope is untouched (retention of the publisher's own text stays §9 deployment-defined). An omission counter (history_lead_id_omitted_total) is the operational alert that a publisher is minting contact-shaped ids. Blocking tests: vec: history-request-row-identifier-shape-pins (negative shapes: E.164-shaped id, email-shaped id, 900+ char id), plat: test_history_planted_contact_in_lead_id_rejected_or_pinned, plat: test_history_legacy_nonconforming_lead_id_omitted. Residual risk, named rather than argued away: the pins are bounded heuristics. They refuse the §3 contact shapes, unbounded stuffing, and the shipped-dossier plant; they do not claim to recognize every conceivable contact encoding inside 64 charset-safe characters. A publisher smuggling a bespoke encoding into its own ids remains a counterparty-data problem under §9 (the data is the publisher's, the rows are scoped to parties already holding it), not something a read projection can structurally prevent.

The caller_phone_hash filter parameter uses the identical rule: the caller submits a digest it computed under its own pair secret (a value it could only have obtained from that pair's pings/posts), and the platform tests membership against the plaintext it holds. Plaintext never leaves; the platform learns nothing it can attribute; a non-pair caller's digest matches nothing. A reviewer should note the cost honestly: the reference platform evaluates the HMAC per candidate row inside the caller's visible scope (O(rows-in-scope) HMACs per filtered query — fine at reference scale; an index-able keyed-lookup scheme is an implementation-phase optimization, not a protocol question).

Tenant binding at query time (new obligation, #202 F2)

The matrix previously presented credential→tenant equality alongside "the shipped multi-tenant list pattern" as if the platform already enforced it. The ARB lane executed the shipped code and the framing was wrong; it is corrected in record. No shipped read path binds a reader credential to a tenant. authorize_lead_read (router.py:1646-1658) filters by counterparty only — a '*'-scoped credential provisioned in tenant-b reads a tenant-a lead through the real dispatch path with 200 (dossier attempt 13). The cited offer-listing precedent scopes by config.routing_tenant_id — a deployment config value fed to store.list_offers(tenant_id=…) (router.py:1773-1780), not by the caller's credentials.tenant_id; test_platform.py:792-805 exercises that store parameter, not a credential. LEP-0005 therefore does not inherit a protection that does not exist: tenant equality is a new obligation this surface adds (it is stricter than the shipped lead-read precedent). The shipped cross-tenant lead-read gap is itself filed to the platform lane via #202 F2; this record binds its own surface and commits the stronger rule.

Enforcement design — following the single-decision-point discipline of LEP-0003's slot award (one transaction resolves the decision; nothing downstream re-decides):

  1. One decision point. A single row-builder in the implementation (history_rows, reference platform) composes the union of the projection tables from the row universe above, and the tenant predicate leads.tenant_id = :caller_tenant appears exactly once, at that outer join. The route, the service dispatch, and the MCP adapter consume its output and add no second filter; per-row tenant checks in response serialization are an implementation bug, not defense-in-depth — by then the row set has already crossed the boundary.
  2. Credential-sourced, never query-sourced. :caller_tenant resolves through auth.tenant_for (auth.py:202-208) for the authenticated sender at dispatch time — the same posture as the Security section's rule that "authorization is computed from the authenticated credential, never from query text". A tenant query parameter does not exist and MUST NOT be added.
  3. Child-table attribution. The row-minting child tables — pings/ bids/deliveries/lifecycle_events — carry no tenant_id column (nor does dead_letter_jobs, which is out of the v1 row universe anyway; storage.py:623-675, storage.py:718-741); every child row is attributed by joining its lead_id to the leads parent inside the same builder. A child row with no parent is unattributable and excluded.
  4. No wildcard bypass. '*'/platform:admin satisfy the scope check and broaden an operator's row set within the credential's tenant only — tenant equality is row-scoping, and row-scoping rides inside every scope (bullet above). The '*' shipped-behavior critique stays in record: binding the wildcard to a tenant is a floor, not a fix, for a surface disclosing prices and timing graphs.

Privacy, security, and universal-core audit

Privacy.

  • The row set is the roadmap's metadata list — status, ids, timestamps, sender/receiver, vertical, price — plus one contact-derived value under the per-pair rule. sender_id/receiver_id/lead_id are organization- and record-level identifiers the caller already holds for in-scope rows (lead_id is publisher-supplied text, pinned at the projection by rule 6 — see the residual-risk note there); cross-party rows are never returned, so the surface discloses no new relationship graph beyond the caller's own transactions (contrast: an operator wildcard does, by design, and is critiqued in the matrix).
  • caller_phone_hash is keyed per credential pair. The information it carries is exactly "does this lead's consumer match a phone you can already compute this digest for" — the membership oracle §9 has provided since v1.0 pings; the log surface adds timing and record state around it, not identifiability. Enumeration inside a pair is that pair's pre-existing insider threat model (spec/05-capabilities.md:134-140; spec/01-transport.md:7-13), unchanged.
  • Hashes remain personal data ("hashes of contact data used for matching are still personal data under most regimes" — carried honestly from LEP-0003's privacy section, issue-tracked there): mitigations are the read-time-only rule (nothing new is stored), per-pair keying (no cross-pair linkage), and erasure (below).
  • PII discipline vs §9: ping-side data is untouched (strict allowlist still excludes everything, §12); this surface exposes contact hashes only over TLS-authenticated GETs, never on pings, never on webhooks.

Erasure/retention integration (the §9 interplay the trigger names).

  • §9: "PII retention policies are deployment-defined" (spec/01-transport.md:89). The history surface introduces no second copy of anything: it projects the platform's own operational tables, so retention, deletion, and suppression already normed per-deployment apply unchanged; the surface MUST NOT be implemented by snapshotting envelopes into new long-lived storage (that would extend retention through a read API — prohibited).
  • Erased consumers must not reappear: erase_lead redacts envelopes and marks rows ERASED/REDACTED (storage.py:2694-2742) and deletes contacted_parties (storage.py:2771-2775); because the keyed hash is computed from held plaintext at read time, post-erasure rows are contact-free in every platform-derived field (valid example C: no consumer member can exist, and no preimage remains to key a hash against) — a caller_phone_hash filter cannot match an erased lead. The one member erase_lead retains is the publisher-minted lead_id (storage.py:2800-2805), which erasure does not scrub; it is gated at emission by the rule-6 pins, not by the redaction whitelist — "structurally contact-free" held for members before this revision and stopped holding for planted identifier text at the dossier's executed attempt 7. This pair of guarantees is asserted as blocking vectors, not trusted to prose: plat: test_history_phone_hash_filter_misses_erased_leads and plat: test_history_rows_after_erase_have_no_contact_derived_fields (the shipped redaction suite is the baseline these extend), together with plat: test_history_planted_contact_in_lead_id_rejected_or_pinned (rule 6) closing the whitelist-retained-text path.
  • Row existence after erasure (ids, statuses, timings) is the erasure-proofing audit trail §9's compliance posture needs to prove an erasure happened — the same trade the shipped code documented ("Immutable routing/audit identifiers remain so operators can prove that an erasure occurred without retaining the consumer payload", storage.py:2690-2693). Deployments whose retention profile requires purging even those identifiers MAY delete rows; the history surface loses them identically. No protocol floor beyond §9 is added.

Security.

  • Query integrity: the HMAC canonical covers <timestamp>\n<idempotency-key>\n<raw-request-body> (spec/05-capabilities.md:96-106) — for GETs the body is empty, so query parameters are not signed. Recorded honestly as an inherited property of every existing read (/v1/lcp/offers?vertical=, attachments, quota), protected by TLS §9; filters disclose nothing to an attacker who can tamper (tampering yields errors or fewer rows), and authorization is computed from the authenticated credential, never from query text.
  • Abuse cases: (a) cross-tenant enumeration — the new tenant binding at query time (single decision point, no wildcard bypass; not a shipped protection, see the matrix section) + authz matrix + per-sender §9 rate limits (storage.py:694, service.py:72 429); (b) timing/price intelligence aggregation — the strictest rule in the matrix: a buyer never sees another buyer's rows, so repeated queries reconstruct only its own history; (c) the operator wildcard — mitigated by field rules inside operator scope and the critique above; (d) log side-channels — the platform MUST audit the query itself (insert_audit action history.query) with filter names, result count, and X-LCP-Request-Id correlation, but MUST NOT log caller_phone_hash values or returned rows (row contents are partially personal data; re-duplicating them into logs breaks the no-second-copy rule); (e) DoS via unbounded scans — limit ≤ 200, cursor keyset (no OFFSET rescans), deployment MAY cap from span.
  • Universal-core audit (§12, item by item where this proposal touches): no vertical-specific or market-specific fields in core (the row's vertical is an opaque id from the registry; a gutter lead in AU, a solar lead in US, and a call lead in NZ all project identically — the endpoint is vertical-agnostic and country-agnostic); phone E.164 / phone_hash HMAC-per-pair line: honored by reusing the §9 primitive (messages.py:48-62), no new hash construct; ping allowlist untouched; message.type enum untouched; open/closed enum policy: status filter is open (§6), message_type/direction closed, stated; "legacy production wire contract fields map 1:1": the reference network's log parameters (ID → request_id, response status → status, caller phone → caller_phone_hash keyed, response phone → same field, time range → from/to, pagination in headers → X-LCP-Result-Count / X-LCP-Total-Results / Link) — adopted as mechanism, with the unsalted-hash inversion of §9/LEP-0003 applied: the network's plaintext phone filter is not adopted. Checklist re-runs at implementation merge.

Alternatives considered

  • Keep it deployment-specific ops tooling (SQL views / extend admin.py only). The decision rules demand this alternative be analyzed, so seriously: admin.py already ships dead-letter list (admin.py:38-41) and list_audit_events already exists internally (storage.py:1085), proving the data answerable today without any protocol change — this LEP does not claim otherwise. It fails on who is asking. The trigger names two audiences split across organizational lines: "platform operators and publishers". A publisher is a different legal entity from the platform; a CLI on the platform's box is unreachable by the party with the dispute, and each publisher building a bespoke side-channel against one deployment multiplies the disclosure risk (ad-hoc exports routinely leak plaintext where this design structurally cannot). The reference network's log exists precisely because dispute resolution is cross-organization — both parties must reconcile against the same authenticated record — which is interop, not operations. Honest balance sheet: the evidence base today is one external production mechanism plus roadmap wording, no LCP adopter has spoken; the #187 evidence ask is the gate that resolves this, and if adopters answer "SQL suffices," Deferred is the legitimate disposition (LEP-0001's deferral shows the precedent with teeth). Note what the two-adopter rule literally gates: a new universal message type; this adds none — the interop-necessity framing above is the honest substitute for the mechanical bar, not a way around one.
  • Registered extension namespace ({org}.ops.history). Structurally impossible for this feature: extensions travel in payload.extensions inside messages (EXTENSION-REGISTRY.md "Extension payload location"), and there is no message here — the feature is a read API; and LEP-0003's alternatives analysis already measured that the closed message objects (ping/bid/post, additionalProperties: false) reject extension-framed fields outright. Nothing to register.
  • Grow GET /v1/lcp/leads/{lead_id} into the search surface. Rejected: it is a single-resource detail view keyed by an id the disputing party often does not have (a call-center log has a phone and a timestamp; the lead id is what you're trying to find), returns per-lead event payloads this record excludes, and paginating it (id-range scans) per lead breaks both the time-range filter and the header-pagination pattern the roadmap names. lead_status remains the right detail view; history rows point at it (lead_id) rather than duplicating it.
  • Push subscriptions instead of pull (LEP-0001). Different capability (streams of transitions vs. lookup of current stored state including records from before any subscriber existed); LEP-0001 is Deferred with an unmet trigger; adopting pull now and optionally push later is composition, not competition.
  • Return redacted envelope bodies ("the JSON minus PII fields"). Rejected — a scrubber is a bug farm (nested free-text fields carry phones: notes, vertical attributes strings), and "return metadata" is the roadmap constraint's actual word. The closed row allowlist is the un-forgettable version of "redact."
  • Return unsalted SHA-256/SHA-1 phone digests so any party can match. Rejected outright (roadmap: "LCP must use its existing per-pair HMAC-SHA256 … cannot be brute-forced"; §14 B3; LEP-0003 alternatives — mechanism yes, that hash never).
