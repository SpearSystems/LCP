# LCP v1.1 roadmap

> **Status:** planning document; the v1.0 protocol contract remains stable.
>
> v1.0.1 is the current implementation release; v1.1 work must be additive,
> evidence-driven, and versioned. A roadmap item
> is not a promise to change the universal core. A feature stays in the
> reference platform or a namespaced extension when that is sufficient.

## Completed foundations

- v1.0 schemas, examples, conformance vectors, OpenAPI, SDK bundles, and
  signed release evidence.
- Home-services category modeling under one `home_services` vertical.
- Versioned publisher mappings and source-record audit digests.
- Non-blocking generated-attribution normalization.
- Versioned buyer requirement profiles and exact named service-area extensions
  in the reference platform.
- Conservative indexed offer candidate selection with fallback-safe routing,
  regression thresholds, and a non-publishing PostgreSQL 18.4 performance job.
- Adoption-readiness metrics and a lightweight LEP proposal process.

## Phase 1 — adoption and governance

### High priority

- Add a second maintainer/reviewer and independent release approval.
- Use the LEP process for external protocol proposals.
- Review GitHub, registry, documentation, and voluntary adopter signals monthly.
- Improve first-implementation guides based on actual issue and adopter data.
- Publish the deferred spec website and announcement only when there is a
  maintained canonical-source publishing workflow.

### Medium priority

- Consider dual licensing for normative specification text if a standards
  community requires a separate documentation license.
- Add a hosted conformance service only if self-hosted vectors are insufficient
  for adopters or certification partners.

## LEP status

The LEP process is adopted for material protocol, schema, extension, security,
privacy, lifecycle, and cross-language changes. The registry is the canonical
status index; this table is a roadmap navigation aid.

| LEP | Scope | Status | Next gate |
|---|---|---|---|
| [LEP-0001](../governance/LEPs/LEP-0001-batch-submission-and-event-subscriptions.md) | Bounded batch submission and event subscriptions | **Draft** — not accepted or implemented | Public discussion, adopter evidence, extension-feasibility analysis, and independent security/privacy review |

## Phase 2 — dynamic buyer criteria

- Expand requirement profiles only with typed, allowlisted operators and
  versioned path registries.
- Add reusable profile storage, effective dates, activation/rollback, and
  explainable match audit records at the platform layer.
- Add richer service-area profiles only when exact versioned sets become too
  large or fragile. Prefer named postal/region sets before polygons.
- Keep buyer-specific minimum volumes, quality rules, compliance rules,
  service categories, and temporary exceptions in offer profiles or
  namespaces, not in the universal core.

## Phase 3 — higher-volume delivery (triggered)

### Bounded batch submission

**Trigger:** independent publishers need bulk intake, backfills, or materially
lower request overhead. Measured baseline: single-process SQLite intake
saturates around 54 records/sec and the full active-offer list is scanned per
lead, so bulk intake is the first scaling lever once a publisher exceeds a few
hundred leads per minute.

**Design constraints:** maximum item count and body size, per-item idempotency,
per-item acknowledgement, partial success, retry only failed items, and no
cross-item transaction. Add the MCP and REST surfaces together with vectors and
SDK helpers.

### Event subscriptions

**Trigger:** polling or configured per-offer webhooks cannot meet latency,
volume, or integration-management requirements.

**Design constraints:** authenticated subscription registration, explicit event
allowlists, tenant authorization, signed at-least-once delivery, stable event
IDs, replay/cursor support, retry/dead-letter behavior, and privacy-safe
filters. Do not turn arbitrary consumer fields into subscription filters.

## Phase 4 — production scale validation (triggered)

**Measured baseline (reference platform, synthetic data, single process):**

- Matching alone reaches roughly 3,900 records/sec with 24 offers and 1,240
  records/sec with 96 offers; every lead scans the full active-offer list.
- SQLite intake and routing saturate around 50 records/sec single-process;
  million-record SQLite intake extrapolates to about five hours and 14 GB,
  which is a local-reference profile, not a production one.
- Buyer webhook latency dominates delivery throughput; delivery work must be
  parallelized once per-webhook latency exceeds a few milliseconds.
- Initial local PostgreSQL 18.4 baseline with four concurrent intake workers
  reached about 54 records/sec for 4,000 records and 24 offers with zero
  errors. With two delivery workers, 500 direct posts and a synthetic 20 ms
  loopback webhook reached about 26.6 deliveries/sec and 12.1 end-to-end
  records/sec. These are directional single-container measurements, not
  production capacity guarantees.
- Candidate-index validation against PostgreSQL 18.4 reached about 100
  records/sec for 4,000 records and 96 offers with four workers and zero
  errors. A fresh 500-record delivery database reached about 14 records/sec
  intake, 57 deliveries/sec, and 11 end-to-end records/sec with two delivery
  workers and 20 ms loopback latency. The CI thresholds intentionally sit below
  these local observations to detect meaningful regressions without treating a
  developer laptop as a capacity guarantee.

### Concurrent Postgres capacity validation

**Trigger:** multiple publishers and buyer webhook volumes push past the
single-node SQLite profile, or before promising multi-node production.

**Work items:**

- Keep the concurrent Postgres benchmark harness
  (`tools/benchmark_postgres_platform.py`) in sync with the platform and run
  it in CI against the Postgres service with capacity baselines, so the
  production profile is validated instead of assumed. The non-publishing
  `performance.yml` job now runs this with artifact reports and thresholds.
- Add index or cached offer candidate selection (vertical, country, category,
  region, service-area profile) so intake stops scanning every active offer
  per lead. The reference platform now implements this as a conservative
  denormalized index; uncertain offers remain fallback candidates and the
  full matcher still decides every result.
- Separate the hot intake path from audit and match-decision history writes;
  keep history writes asynchronous or retention-bounded.
- Add retention, archival, and partitioning for encrypted envelopes and
  decision history before volume makes storage unbounded.

## Deferred protocol and marketplace work

### Rich geographic predicates

**Trigger:** exact country/state/postal lists and named service-area sets become
operationally too large or inaccurate.

**First step:** versioned service-area datasets with explicit source, effective
time, and audit identity. Defer polygons, geocoding, and external boundary
providers until the deployment can operate those dependencies safely.

### Multi-currency auction semantics

**Trigger:** buyers in different currencies must compete in the same auction.

**Required design:** auction currency, original bid currency and amount, FX
source, rate timestamp and validity window, deterministic rounding, stale-rate
behavior, and explicit settlement currency. Never compare raw minor-unit
numbers from different currencies.

### Richer offer predicate language

**Trigger:** named profiles and the current equality/allowlist predicates are
insufficient for repeated independent buyer requirements.

**Guardrails:** small allowlisted operator set, typed schema paths, no arbitrary
code or expressions, explainable failures, performance limits, and no
predicate-driven PII leakage into pings.

### Other deferred items

- `submit_leads_batch` and `subscribe_to_events` in the normative MCP/REST
  contract.
- `PROCESSED` delivery acknowledgement when CRM synchronization needs a
  distinct post-transport state.
- Multi-currency pricing and cross-border auction ranking.
- Hosted conformance and certification workflow.
- Split `SPEC.md` only if it exceeds the documented readability threshold or
  contributor workflow requires multiple normative documents.
- Formal PII sensitivity taxonomy, raw post-only IP/address guidance, and
  raw-form evidence extensions when adopter contracts require them.

## Change gates

Every v1.1 candidate must update, as applicable:

1. schemas and extension registrations;
2. examples and negative examples;
3. conformance vectors and reference-platform tests;
4. generated SDK models, schema bundles, and manifests;
5. OpenAPI/MCP contracts;
6. compatibility and deprecation notes;
7. changelog, decision record, and release evidence.

No roadmap item silently changes the published v1.0 protocol contract.
